# Архитектура и реализация видеоконвейера на C++

Документ описывает учебный проект: **захват видео с USB-камеры (`/dev/videoX`) → инференс ONNX-модели instance-сегментации → визуализация двух потоков (сырой кадр и кадр с масками) в реальном времени**. Без трекинга — трекинг добавляется позже, архитектура оставляет для него место.

Документ устроен так, чтобы его можно было читать параллельно с кодом: каждый раздел ссылается на конкретные файлы в `src/`.

---

## 1. Постановка задачи и ограничения реального времени

Задача выглядит простой — «взять кадр и прогнать через нейросеть» — но в реальном времени она упирается в четыре физических ограничения:

| Ограничение | Что происходит, если его игнорировать |
|---|---|
| **Камера отдаёт кадры по своему расписанию** (30 fps ⇒ каждые 33.3 мс) | Блокирующее чтение в общем потоке останавливает всё остальное |
| **Инференс непредсказуем по времени** (5–50 мс, зависит от кадра, CPU, thermal throttling) | Задержка растёт: экран показывает всё более старые кадры |
| **Буферы драйвера ограничены** (обычно 4 mmap-буфера) | Если не успеваем «возвращать» буферы (`VIDIOC_QBUF`), камера теряет кадры на уровне железа |
| **UI обязан обновляться часто** (~30 fps), иначе картинка дёргается | Показ устаревшего результата на 3 кадра назад выглядит как «тормоза» |

Из этого следует главное архитектурное решение: **разделить захват, инференс и отображение на независимые потоки, связав их очередями фиксированной ёмкости, которые выбрасывают устаревшие кадры**. Это классический паттерн **pipeline с backpressure по политике "последний кадр важнее"**.

```
 ┌──────────────┐    ┌────────────────────┐    ┌───────────────┐    ┌────────────────┐
 │ V4L2Source   │───▶│ BoundedQueue<      │───▶│ Inference     │───▶│ BoundedQueue<  │───┐
 │ (поток 1)    │    │ FramePtr> (2)      │    │ loop (поток 2)│    │ ResultPtr> (2) │   │
 │ poll+DQBUF   │    │ DropOldest         │    │ ONNX Runtime  │    │ DropOldest     │   │
 └──────────────┘    └────────────────────┘    └───────────────┘    └────────────────┘   │
                                                                                          ▼
                                                             ┌──────────────────────────────────┐
                                                             │ UI-поток (main): Renderer        │
                                                             │ side-by-side + HUD + waitKey     │
                                                             └──────────────────────────────────┘
```

Три потока — минимум, при котором камера никогда не ждёт модель. Захват может идти 30 fps, модель — 8 fps, а экран при этом будет обновляться с частотой модели, но **всегда самыми свежими данными**, с постоянной задержкой ≈ (1 кадр камеры + время инференса), а не с растущей очередью.

## 3. Ключевые структуры данных

### 3.1 `Frame` — единица передачи между потоками

```cpp
struct Frame {
    std::shared_ptr<const cv::Mat> image;  // CV_8UC3, BGR
    std::uint64_t seq = 0;                 // монотонный номер от источника
    SteadyClock::time_point t_captured{};  // момент получения буфера от драйвера
    SteadyClock::time_point t_decoded{};   // момент готовности пикселей в cv::Mat
};
using FramePtr = std::shared_ptr<const Frame>;
```

Решения и почему именно так:

1. **`shared_ptr<const cv::Mat>`, а не `cv::Mat` по значению.** `cv::Mat` — это дескриптор: копирование дешёвое (счётчик ссылок на буфер, O(1)). Но `cv::Mat` **не потокобезопасен при записи**: если один поток делает `mat.at<...>() = ...` или `cv::resize` в тот же буфер, другой увидит разорванные данные. Обёртка в `const` превращает это в ошибку компиляции: из `Frame` физически нельзя получить неконстантные пиксели, не сделав `clone()`. Потокобезопасность получается **на уровне типов**, а не на мьютексах.
2. **`shared_ptr<const Frame>` снаружи** — чтобы кадр мог одновременно «жить» в очереди, в результате инференса и в UI (например, если нужно нарисовать и сырой, и размеченный вид одного кадра). Время жизни определяется счётчиком ссылок; никто не владеет кадром «единолично», поэтому не нужны `unique_ptr` + ручное клонирование.
3. **`steady_clock`, а не `system_clock`.** Для измерения задержек нужны монотонные часы: `system_clock` может прыгнуть при синхронизации NTP и дать отрицательную латентность. `t_captured` ставится **сразу после `VIDIOC_DQBUF`** (до конвертации), `t_decoded` — после конвертации формата; разница `t_decoded − t_captured` показывает именно стоимость декодирования MJPG/YUYV, без времени ожидания в `poll`.
4. **`seq`** — диагностика потерь: в HUD видно, сколько кадров камера отдала, а сколько дошло до модели. Разница = вытесненные из очереди кадры.

### 3.2 `Instance` и `InferenceResult` — результат инференса

```cpp
struct Instance {
    int class_id = -1;
    float score = 0.0f;
    cv::Rect2f box;  // в пикселях исходного кадра
    cv::Mat mask;    // CV_8UC1, 0/255, размер исходного кадра
};

struct InferenceResult {
    std::shared_ptr<const Frame> frame;  // к какому кадру относится разметка
    std::vector<Instance> instances;
    InferTimings timings;   // pre / run / post, мс
    double latency_ms;      // от получения буфера камеры до готовой разметки
    int input_width, input_height;
};
using ResultPtr = std::shared_ptr<const InferenceResult>;
```

* **`cv::Rect2f`, а не `cv::Rect`** — координаты после обратного letterbox-преобразования дробные. Округление до целых на этом этапе смещает маску относительно изображения на 1–2 пикселя, что заметно на мелких объектах.
* **Маска в размере исходного кадра** (а не 160×160 от прототипов) — сознательный обмен памяти на простоту: рендерер просто накладывает её без дополнительных преобразований координат. Для 1280×720 это 900 КБ на объект; при 10 объектах — 9 МБ, что для одного кадра приемлемо. Если объектов много — маску можно хранить в координатах прототипов и масштабировать при отрисовке.
* **`InferenceResult` передаётся как `shared_ptr<const ...>`** — снимок неизменяем. UI-поток рисует по нему, пока поток инференса уже считает следующий кадр; гонки нет, потому что нет записи.
* **`frame` внутри результата** — это и есть «склейка» двух потоков: разметка всегда отрисовывается поверх того кадра, для которого она посчитана. Никаких «масок от предыдущего кадра на текущем изображении».

### 3.3 `BoundedQueue<T>` — очередь с политиками переполнения

```cpp
enum class OverflowPolicy { Block, DropOldest, DropNewest };

template <class T>
class BoundedQueue {
public:
    bool push(T value);                 // может спать (Block) или вытеснять
    std::optional<T> try_pop();         // не блокирует
    template <class R, class P>
    std::optional<T> pop_wait_for(std::chrono::duration<R, P>);
    void close();                       // разбудить всех, запретить push
    std::uint64_t dropped() const noexcept;
};
```

Почему не `std::queue` + `std::mutex` в вызывающем коде: политика переполнения — это **семантика конвейера**, и она должна быть ровно в одном месте. Три политики покрывают три разных случая:

* **`Block`** нужен там, где терять данные нельзя (запись видео на диск). Производитель засыпает на `not_full_`, пока потребитель не освободит место.
* **`DropOldest`** — правильный выбор для камеры: если модель не успевает, бессмысленно обрабатывать кадр 500-миллисекундной давности; вытесняем самый старый и работаем со свежим. Это и даёт **постоянную задержку** вместо растущей очереди.
* **`DropNewest`** — когда важнее уже накопленное (например, буферизация событий).

Технические детали реализации, важные для понимания многопоточности:

* **`std::mutex` + два `std::condition_variable`** (`not_empty_`, `not_full_`). На `std::condition_variable` нельзя рассчитывать без предиката: возможны «ложные пробуждения» (spurious wakeup), поэтому везде `wait(lock, predicate)`.
* **`std::unique_lock` в `wait`** — потому что `wait` должен отпустить мьютекс на время сна и снова взять его после; `std::lock_guard` этого не умеет.
* **`close()`** — единственный корректный способ остановки потребителя. Флаг `closed_` под тем же мьютексом + `notify_all()`: все спящие просыпаются, видят `closed_ == true` и выходят. Без этого `join()` в деструкторе повис бы навсегда.
* **`std::atomic<std::uint64_t> dropped_`** — счётчик потерь читается UI-потоком, поэтому атомарный; пишется под мьютексом, но `fetch_add` с `memory_order_relaxed` достаточен (нам нужно только приблизительное значение, а не синхронизация данных).
* **Шаблон, а не базовый класс** — очередь используется с `FramePtr` и `ResultPtr`; шаблон даёт мономорфную реализацию без виртуальных вызовов на каждом push/pop (это горячий путь, 30–60 вызовов в секунду на стадию — важна не столько скорость, сколько отсутствие лишних сущностей).

### 3.4 `PipelineStats` — метрики без блокировок

```cpp
struct PipelineStats {
    std::atomic<std::uint64_t> frames_captured{0};
    std::atomic<std::uint64_t> frames_dropped{0};
    std::atomic<std::uint64_t> grab_timeouts{0};
    std::atomic<std::uint64_t> frames_inferred{0};
    std::atomic<std::int64_t>  inference_us{0};
    std::atomic<std::int64_t>  latency_us{0};
    // ...
};
```

Идея: **счётчики пишут рабочие потоки, читает UI**. Если бы это был обычный `struct` под мьютексом, UI-поток на каждом кадре блокировал бы инференс ради чтения четырёх чисел. `std::atomic` с `memory_order_relaxed` даёт и отсутствие блокировок, и достаточную точность (нам не нужна согласованность между полями — каждое число само по себе осмысленно).

`RateMeter` (в том же файле) — пример потоконезависимого класса: живёт только в UI-потоке, поэтому не содержит атомиков. Считает мгновенную скорость между замерами и сглаживает экспоненциальным средним, чтобы цифра в HUD не дёргалась:

```
v ← v·(1−α) + (Δframes/Δt)·α,   α = 0.2
```

## 4. Захват с камеры: V4L2 (`src/video/v4l2_source.cpp`)

### 4.1 Последовательность вызовов

```
open(/dev/videoX, O_RDWR | O_NONBLOCK | O_CLOEXEC)
  VIDIOC_QUERYCAP        — что умеет устройство (capture? streaming?)
  VIDIOC_S_FMT           — согласовать формат: MJPG / YUYV / UYVY, размер
  VIDIOC_S_PARM          — попросить 30 fps (многие UVC-камеры игнорируют)
  VIDIOC_REQBUFS(MMAP)   — попросить N буферов ядра
  VIDIOC_QUERYBUF + mmap — спроецировать каждый буфер в наше адресное пространство
  VIDIOC_QBUF × N        — вернуть все буферы драйверу
  VIDIOC_STREAMON        — «поехали»
```

Далее в цикле `next()`:

```
poll(fd, POLLIN, timeout)  — спим в ядре, пока не появится готовый кадр
  VIDIOC_DQBUF             — забрать заполненный буфер (индекс + bytesused)
  конвертация в BGR        — YUYV→BGR или imdecode(MJPEG)
  VIDIOC_QBUF              — вернуть буфер драйверу (обязательно!)
  TimePoint                — зафиксировать t_captured
```

### 4.2 Почему memory-mapped I/O, а не `read()`

Три способа получать кадры в V4L2:

| Способ | Как работает | Минусы |
|---|---|---|
| `read()` | ядро копирует кадр в наш буфер | лишняя копия целого кадра, нет контроля над количеством буферов |
| **`mmap` (используется)** | ядро пишет прямо в страницы, отображённые в наше адресное пространство | нужен `munmap`, нельзя масштабировать на несколько процессов |
| `userptr` / `dmabuf` | мы сами выделяем память / обмениваемся DMA-буферами | сложность, нужна поддержка драйвера |

`mmap` — «zero-copy» в том смысле, что **драйвер пишет пиксели непосредственно в память, которую мы читаем**: нет промежуточной копии `read()`-ом. Копия остаётся только при конвертации в BGR (её делает OpenCV), потому что модель ждёт плотный `CV_8UC3`.

### 4.3 Конвейер буферов и обязательный `QBUF`

Ключевой момент, на котором ломаются почти все первые реализации: **после `DQBUF` буфер надо вернуть `QBUF`**, иначе через `buffer_count` кадров драйверу нечего заполнять и камера встаёт (в логе — `poll` таймаутами, картинка «замерзает»). В коде `QBUF` вызывается **даже если конвертация упала**:

```cpp
const NextStatus status = convert_frame(buffers_[buffer.index], buffer.bytesused, seq, out, error);
if (xioctl(impl_->fd, VIDIOC_QBUF, &buffer) < 0) {   // всегда!
    LOG_ERROR << "VIDIOC_QBUF после обработки: " << errno_text(errno);
}
return status;
```

Количество буферов (`V4l2Config::buffer_count = 4`) — компромисс: 2 — минимум, чтобы камера не простаивала, пока мы конвертируем; 4–6 дают запас на джиттер планировщика; больше — растёт задержка, потому что в очереди драйвера копится больше «старых» кадров.

### 4.4 Форматы пикселей

| Формат | Байт на пиксель | Плюсы | Минусы |
|---|---|---|---|
| **YUYV** (YUV 4:2:2) | 2 | без декодирования, предсказуемая цена `cvtColor` | по USB 2.0 1280×720@30 — это ~55 МБ/с, часто не влезает |
| **MJPG** | ~0.1–0.3 (зависит от сцены) | влезает в USB 2.0, выше fps и разрешение | декодирование JPEG (~3–8 мс на 720p), артефакты сжатия |
| UYVY, RGB24 | 2 / 3 | — | редки |

Поэтому `prefer_mjpeg = true` по умолчанию, а `--no-mjpeg` переключает на сырой YUYV.

Тонкость, которую часто пропускают: **`bytesperline` (шаг строки) может быть больше `width × bytes_per_pixel`** из-за выравнивания. Если это не учесть, изображение «поедет» по диагонали. В коде шаг передаётся в `cv::Mat` явно:

```cpp
const int step = impl_->stride > 0 ? impl_->stride : info_.width * 2;
const cv::Mat yuyv(info_.height, info_.width, CV_8UC2, const_cast<void*>(data), step);
cv::cvtColor(yuyv, bgr, cv::COLOR_YUV2BGR_YUY2);
```

`cv::Mat` здесь **оборачивает память драйвера без копирования** (`const_cast` нужен из-за API `cv::Mat`, который не принимает `const void*`; данные только читаются). Это работает, потому что `cvtColor` сразу создаёт новый `bgr`. Живёт такая обёртка микросекунды — между `DQBUF` и `QBUF`.

MJPG декодируется как самостоятельный JPEG-файл в памяти:

```cpp
const cv::Mat encoded(1, static_cast<int>(length), CV_8UC1, const_cast<void*>(data));
cv::imdecode(encoded, cv::IMREAD_COLOR, &bgr);
```

### 4.5 Неблокирующий режим + `poll`

Файл открывается с `O_NONBLOCK`, а ожидание делается через `poll()` с таймаутом (`poll_timeout_ms = 500`). Зачем:

1. `DQBUF` без данных вернул бы `EAGAIN`, и пришлось бы крутить busy-loop, сжигая CPU.
2. Бесконечный `poll` не дал бы потоку узнать о `Ctrl+C` — обработчик сигнала прерывает `poll` с `EINTR` (потому что `sigaction` установлен **без** `SA_RESTART`), поток возвращается в цикл, видит флаг остановки и выходит.
3. Таймаут — это ещё и диагностика: `grab_timeouts` в статистике растёт, значит камера не отдаёт кадры (занята другим процессом, отключена, неверный формат).

### 4.6 Обработка ошибок и отключения камеры

* Все `ioctl` идут через обёртку `xioctl`, которая повторяет вызов при `EINTR` — системные вызовы могут быть прерваны сигналом, и это не ошибка.
* `POLLERR | POLLHUP | POLLNVAL` от `poll` → `NextStatus::Error`: устройство физически отключили.
* **`device_caps`, а не `capabilities`.** У многофункциональных устройств (камера с микрофоном, тюнер) поле `capabilities` описывает всё устройство, а возможности конкретного узла `/dev/videoX` — в `device_caps`. Проверка только по `capabilities` ложно отвергает часть камер. Плюс отдельная ветка диагностики для устройств только с multi-planar API: наш код использует одноплоскостной (single-plane) набор структур, и об этом честно сообщается в ошибке с подсказкой `v4l2-ctl --all`.
* **`bytesused == 0`** (пустой кадр — бывает при сбросе экспозиции или пропуске) не конвертируется, но буфер всё равно возвращается в `QBUF`, иначе камера «встанет».
* Поток захвата считает **ошибки подряд**: одиночный сбой не убивает конвейер, но после 30 подряд — конвейер останавливается, чтобы не крутить пустой цикл и не заливать лог.
* Pimpl (`struct Impl`) прячет `fd`, mmap-указатели и `linux/videodev2.h` из заголовка: `v4l2_source.hpp` можно включить в файл, который не должен видеть Linux-специфичные типы, и это упрощает будущий порт на macOS/Windows (там будет другой класс с тем же интерфейсом).

### 4.7 RAII и порядок освобождения ресурсов

Деструктор `~V4l2Source()` вызывает `close_device()`, который соблюдает строгий порядок:

```
VIDIOC_STREAMOFF → munmap(все буферы) → close(fd)
```

`munmap` **до** `close`: отображение памяти, полученное от файла, становится невалидным после закрытия дескриптора. Если перепутать — `SIGSEGV` при следующем обращении (или «тихое» чтение мусора).

## 5. Инференс ONNX (`src/infer/onnx_segmenter.cpp`)

### 5.1 Почему ONNX Runtime

| Вариант | Плюсы | Минусы для этой задачи |
|---|---|---|
| **ONNX Runtime** (используется) | полная поддержка операторов, CPU/CUDA/DirectML, явные настройки потоков, оптимизация графа, стабильный C++ API | внешняя зависимость (~30 МБ .so) |
| `cv::dnn` | ничего не надо ставить сверх OpenCV | отстаёт от новых архитектур, часть операторов YOLO-seg не поддерживается или поддерживается с ограничениями |
| TensorRT | максимальная скорость на NVIDIA | требует конвертации и привязки к GPU |
| LibTorch | «родной» формат Ultralytics | тяжёлый, медленнее на CPU |

Для учебного проекта важна предсказуемость: ONNX Runtime даёт одинаковый результат на любой машине и понятные сообщения об ошибках.

### 5.2 Жизненный цикл сессии

```cpp
Ort::Env env{ORT_LOGGING_LEVEL_ERROR, "videotest"};   // один на процесс
Ort::SessionOptions options;
options.SetGraphOptimizationLevel(ORT_ENABLE_ALL);     // слияния операторов, NCHWc и т.д.
options.SetIntraOpNumThreads(n);                       // потоки внутри одного узла
session = std::make_unique<Ort::Session>(env, path, options);
```

* `Ort::Env` — глобальное окружение (пул потоков, логгер). Создаётся один раз; уничтожается последним.
* `Ort::Session` — потокобезопасен для `Run()`, но у нас модель используется одним потоком, поэтому дополнительные блокировки не нужны.
* `IntraOpNumThreads` — сколько потоков может использовать **один** оператор (например, свёртка). На 2-ядерной машине ставить больше 2 бессмысленно; при конкуренции с потоком камеры лучше оставить 1–2 и не отбирать CPU у декодирования.
* Все типы `Ort::*` — владельческие (RAII): `Ort::Value`, `Ort::Session`, `Ort::AllocatedStringPtr` освобождают ресурсы в деструкторе. Исключения — `Ort::Exception` с `.what()`, ловятся в `segment()` и превращаются в `std::string& error` (исключения **не должны** вылетать из потока: необработанное исключение в `std::thread` вызывает `std::terminate`).

### 5.3 Препроцессинг: letterbox, нормализация, NCHW

Модель ждёт вход `[1, 3, 640, 640]` float32, значения `[0,1]`, порядок каналов RGB.

```cpp
// 1) сохранить пропорции, вписать в 640x640, поля залить серым 114
scale = min(640/w, 640/h);
canvas 640x640 ← resize(bgr, w*scale, h*scale) в центр
// 2) BGR→RGB, /255, HWC→CHW
cv::dnn::blobFromImage(canvas, tensor, 1.0/255.0, Size(640,640), Scalar(),
                       /*swapRB=*/true, /*crop=*/false, CV_32F);
```

Три вещи, которые здесь легко сделать неправильно:

1. **Пропорции.** Если просто `resize` в 640×640, объекты растягиваются, и обратное преобразование координат даёт систематическое смещение, разное по осям. Letterbox это устраняет, а `LetterboxTransform` хранит `scale_x`, `scale_y`, `pad` — **один объект используется и для прямого, и для обратного преобразования**, поэтому невозможно «забыть» применить ту же математику при декодировании.
2. **Серый 114, а не 0.** Так обучали YOLO; чёрные поля дают другую статистику входов и немного просаживают уверенность у объектов на краю.
3. **`swapRB = true`.** OpenCV хранит BGR, модели обучены на RGB. Если забыть — красный и синий поменяются, и точность упадёт не катастрофически, но заметно (это классическая «тихая» ошибка).

Нормализация — перенос в `blobFromImage` (один проход по данным), а не отдельными циклами: меньше проходов по памяти.

### 5.4 Выходы модели и их декодирование

Поддерживаются два формата (выбор автоматический, по форме тензора):

**(A) «Сырой» выход YOLOv8-seg / YOLO11-seg**

```
output0: [1, 4 + nc + 32, 8400]      — предсказания по всем якорям
output1: [1, 32, 160, 160]           — 32 прототипа масок
```

* `nm = 32` — число коэффициентов масок; `nc` — число классов (80 для COCO).
* Раскладка памяти — **канал-мажорная**: значение канала `c` для якоря `a` лежит по индексу `c * 8400 + a`. Отсюда отдельные указатели `cx_row`, `cy_row`, `w_row`, `h_row` — это не «строки», а подряд идущие блоки по 8400 значений.
* Уверенность класса — уже вероятность (после сигмоиды внутри модели), поэтому порог применяется напрямую.
* 8400 = 80² + 40² + 20² — сумма ячеек трёх уровней Feature Pyramid Network.

В коде это читается максимально близко к формуле:

```cpp
for (int64_t a = 0; a < anchors; ++a) {
    float best = 0; int best_class = -1;
    for (int c = 0; c < num_classes; ++c) {
        const float v = prediction[(4 + c) * anchors + a];   // канал класса c, якорь a
        if (v > best) { best = v; best_class = c; }
    }
    if (best_class < 0 || best < score_threshold) continue;
    ...
    for (int k = 0; k < 32; ++k)
        coeff[k] = prediction[(4 + num_classes + k) * anchors + a];
}
```

**(B) End-to-end выход (YOLO26): NMS уже внутри графа**

```
output0: [1, 300, 38]     — 300 готовых детекций: x1,y1,x2,y2, score, class, 32 коэффициента
output1: [1, 32, 160, 160] — прототипы
```

Здесь `N = 300` — это уже top-k после one-to-one head, дубликатов нет, второй NMS **не нужен** (и вреден: он бы удалил легитимные перекрывающиеся объекты, которые модель уже различила).

Тонкость: разные версии экспорта отдают либо `x1,y1,x2,y2`, либо `cx,cy,w,h`. Код определяет формат по первой «непустой» строке:

```cpp
xyxy_format = (row[2] >= row[0]) && (row[3] >= row[1]);
```

Это эвристика, но она проверяема: для `cx,cy,w,h` условие почти всегда ложно, для `xyxy` — почти всегда истинно (кроме вырожденных строк, которые отсеиваются порогом).

### 5.5 NMS (class-aware)

Для «сырого» выхода остаётся ~10–100 кандидатов выше порога, и многие боксы — дубликаты одной и той же собаки. NMS реализован сам, в `src/infer/nms.hpp`:

```cpp
std::iota(order.begin(), order.end(), 0);                 // индексы 0..n-1
std::stable_sort(order.begin(), order.end(), /* по убыванию score */);
for (i : order) {
    if (suppressed[i]) continue;
    keep(i);                                              // самый уверенный остаётся
    for (k : order после i)
        if (тот же класс && IoU(keep, k) > порог) suppressed[k] = 1;
}
```

* **`IoU`** = площадь пересечения / площадь объединения; реализован отдельной функцией `box_iou` и покрыт тестами (включая вырожденные боксы с нулевой площадью — чтобы не было деления на ноль).
* **Почему class-aware**: объекты разных классов часто перекрываются (человек держит чашку). Подавление по всем классам склеило бы их в один объект.
* **Почему не `cv::dnn::NMSBoxes`**: пятиаргументная перегрузка класса не учитывает, а вызов `cv::dnn` ради одной функции тянет лишнюю зависимость и скрывает алгоритм — а в учебном проекте важно видеть его целиком.
* **Сложность**: O(n²) в худшем случае, но n после порога — десятки, а не 8400. Сортировка плюс ранний выход по `max_detections`.
* **Синхронность с масками**: `coeffs` перемещаются вместе с боксами, иначе маски «переедут» на чужие объекты. Это тоже проверяется тестом (`nms_suppresses_duplicates` сверяет маркеры коэффициентов).

Для end-to-end выхода (YOLO26) NMS **не применяется** — он уже выполнен внутри графа (one-to-one head), повторное подавление удалило бы легитимно перекрывающиеся объекты. Ограничение `max_detections` применяется в обоих случаях.

### 5.6 Сборка масок из прототипов

Инстанс-сегментация YOLO не выдаёт маску на каждый объект. Вместо этого модель выдаёт **базис из 32 «мягких масок»** (прототипы 160×160) и **32 коэффициента на объект**. Маска объекта — их линейная комбинация:

```
mask(x, y) = sigmoid( Σ_k coeff[k] · proto[k, y, x] )
```

Что делает `build_masks`:

1. **Аккумуляция в один проход**: для каждого `k` прибавляем `coeff[k] · proto[k]` к `cv::Mat combined` (CV_32F, 160×160). Это и есть маленькое матричное умножение 32×25600.
2. **Обрезка по боксу** (в координатах прототипов: `ratio = 160/640 = 0.25`). Обрезка важна не только ради скорости: за пределами бокса линейная комбинация может дать «мусорные» пятна, которые дадут ложные маски.
3. **Ресайз** обрезанной области до размера бокса **в исходном кадре** (`INTER_LINEAR` — маска на выходе гладкая, и билинейная интерполяция даёт аккуратные края).
4. **Порог в логитах**: `sigmoid(v) > t` эквивалентно `v > logit(t)`, поэтому вместо поэлементных `exp()` и деления достаточно одного сравнения с `log(threshold/(1−threshold))`. Результат тот же, а на маске 640×480 экономится заметное время.
5. **Вставка в кадр** размером с исходное изображение в координатах `LetterboxTransform::to_source(box)`.

Почему сигмоида после ресайза, а не до: `sigmoid` — монотонная функция, поэтому порядок не влияет на результат *пороговой бинаризации по интерполированным значениям* — но выполнение после ресайза на меньшей матрице дешевле. (В нашем случае ресайз идёт «вверх», поэтому выигрыша по объёму нет, но логика та же и код проще.)

### 5.7 Метаданные модели: имена классов

Ultralytics кладёт имена классов в `metadata["names"]` как python-dict:

```
{0: 'person', 1: 'bicycle', ...}
```

Это не JSON (одинарные кавычки), поэтому `parse_class_names` заменяет `'` на `"` и разбирает пары вручную, без сторонних библиотек. Если метаданных нет, имена генерируются как `class_0`, `class_1`, … — программа остаётся работоспособной.

Число классов тоже не «зашито»: оно вычисляется из формы выхода (`4 + nc + 32 = channels`), с перекрёстной проверкой по числу имён из метаданных. Поэтому одна и та же сборка работает и с COCO-моделью (80 классов), и с моделью на 1–5 классов.

### 5.8 Производительность и тайминги

`segment()` измеряет три фазы: `preprocess`, `run`, `postprocess`. Значения уходят в `InferTimings` и в HUD. Типичные порядки для 640×640 на CPU:

| Фаза | Время | Что dominирует |
|---|---|---|
| preprocess | 1–3 мс | `resize` кадра 1280×720 → 640×640, `blobFromImage` (копия + конверсия) |
| inference | 8–40 мс | свёртки, зависит от модели (n/s/m) и числа потоков |
| postprocess | 1–4 мс | NMS + сборка масок (32 × 25600 float-операций на объект) |

Практические рычаги ускорения (в порядке отдачи): уменьшить `imgsz` до 480/320 → взять модель `n` вместо `s/m` → `--infer-device cuda` → 2 потока вместо 4 на слабом CPU. Отрисовка 10 масок методом `setTo` по маске 1280×720 стоит ~2–4 мс — если станет узким местом, маски можно хранить в 160×160 и растягивать при отрисовке.

## 6. Конвейер и многопоточность (`src/pipeline/pipeline.cpp`)

### 6.1 Потоки и их обязанности

| Поток | Где | Что блокирует | Что делает |
|---|---|---|---|
| capture | `capture_loop` | `poll()` до 500 мс | `DQBUF` → конвертация → `push` в `capture_queue_` |
| inference | `inference_loop` | `pop_wait_for(100ms)` | `pop` → `segment` → `push` в `result_queue_` |
| UI | `main` | `pop_wait_for(10ms)`, `cv::waitKey(1)` | `draw` → `compose` → `imshow` |

Почему именно **два** рабочих потока, а не один: захват должен продолжаться, пока модель считает. Если совместить, время кадра станет `t_grab + t_infer` (33 + 20 = 53 мс ⇒ 19 fps вместо 30), а задержка вырастет на время инференса. С двумя потоками камера идёт на своих 30 fps, модель — на своих ~50 fps (или 15, если она тяжёлая), а UI всегда берёт самый свежий результат.

### 6.2 Жизненный цикл и остановка

```cpp
Pipeline::start();   // создаёт std::thread ×2
Pipeline::stop();    // идемпотентна
```

Корректная остановка — самая частая причина «зависаний при выходе». Здесь порядок такой:

1. `running_ = false` (`std::atomic<bool>`).
2. `capture_queue_.close()` → потребитель проснётся из `pop_wait_for` по `not_empty_` и увидит `closed_`.
3. `result_queue_.close()` → UI-цикл завершится.
4. `join()` обоих потоков.

Дополнительно работает **кооперативный флаг сигнала** (`core/signal_flag.*`):

```cpp
// обработчик сигнала — только атомарная запись, ничего больше
extern "C" void handle_signal(int) { g_stop.store(true, std::memory_order_relaxed); }
```

Почему обработчик сигнала не может делать больше: в нём запрещены функции, не являющиеся async-signal-safe (мьютексы, `malloc`, `printf`). Если попытаться «остановить конвейер прямо в обработчике», получим deadlock или повреждение кучи. Поэтому `static_assert(std::atomic<bool>::is_always_lock_free)` гарантирует, что запись флага не возьмёт внутренний мьютекс.

`sigaction` ставится **без** `SA_RESTART`, чтобы `poll()` и `condition_variable::wait` прерывались и поток быстрее замечал флаг.

### 6.3 Почему не `std::jthread`

В C++20 есть `std::jthread`, который умеет останавливаться через `std::stop_token`. Он был бы удобен, но:

* поддержка в libstdc++ появилась в GCC 10, а `stop_token`/`condition_variable_any` в связке — позже и с ограничениями;
* `stop_token` не помогает там, где блокировка происходит **внутри ядра** (`poll`, `DQBUF`) — прерывание всё равно приходит как `EINTR`, и сигнал нужно обрабатывать отдельно.

Поэтому используется явный `std::atomic<bool> running_` + `close()` очередей + таймауты в `wait`. Это работает на любом компиляторе C++17/20 и делает механику остановки видимой.

### 6.4 Искусственная задержка как учебный инструмент

`--delay-ms 100` добавляет `sleep` в поток инференса. Это позволяет **увидеть** поведение системы при медленной модели:

* HUD показывает `dropped` (кадры, вытесненные из очереди) — растёт;
* `latency` остаётся ~постоянной (100 мс + время кадра), а не растёт до секунд — именно потому, что очередь вытесняет старое, а не копит;
* без `DropOldest` (если временно поменять политику на `Block`) вы увидите обратную картину: латентность растёт линейно, картинка отстаёт всё сильнее, а fps падает до fps модели. Это лучшая демонстрация того, зачем нужна политика вытеснения.

## 7. Визуализация (`src/render/renderer.cpp`)

### 7.1 Два потока рядом

```cpp
cv::Mat overlay = renderer.draw(raw, *result, class_names);   // размеченный кадр
cv::Mat canvas  = renderer.compose(raw, overlay, Layout::SideBySide);
// hconcat: [ raw | overlay ] — одинаковые тип и высота обязательны
```

`cv::hconcat` требует одинаковых типов и числа строк, поэтому `compose` проверяет размер и при необходимости ресайзит правую часть. Разделитель (`cv::line`) и подписи половинок сделаны поверх результата — это просто, но сильно помогает читать картинку.

`Layout::OverlayOnly` нужен для `--record`: запись полного side-by-side в 2× ширину — лишние мегабайты.

### 7.2 Порядок и способ отрисовки масок

```
1. layer = clone(raw)
2. для каждой маски: layer.setTo(color_of_class, mask)     — заливка по бинарной маске
3. addWeighted(raw, 1−α, layer, α, 0, out)                 — одно смешивание на все маски
4. findContours + drawContours                             — чёткая граница
5. rectangle + putText                                     — бокс и подпись
```

Почему один `addWeighted`, а не наложение каждой маски с альфой: при последовательном наложении полупрозрачных заливок **перекрывающиеся области темнеют/насыщаются** (α складывается). Один слой + одно смешивание даёт равномерную прозрачность независимо от количества объектов.

`cv::findContours` **модифицирует входную матрицу** (историческая особенность OpenCV), поэтому маска клонируется — иначе испортили бы `InferenceResult`, который может читаться в другом потоке.

### 7.3 Читаемость текста

`put_label` рисует чёрную подложку под текст: на светлом кадре белые буквы без фона нечитаемы. `cv::getTextSize` даёт размеры заранее, поэтому рамка не обрезает текст, а `putText(..., cv::LINE_AA)` включает сглаживание.

### 7.4 HUD

Панель в левом верхнем углу: `capture fps | infer fps | captured`, `source WxH | uptime`, `infer ms | latency ms | dropped`, `queue depth | objects`. Подложка — умножение ROI на 0.45 (`roi.convertTo(roi, -1, 0.45, 0)`), а не `addWeighted` с копией — на один проход меньше.

Здесь же — практический урок: `capture fps` и `infer fps` **должны расходиться** при медленной модели, и это нормально. Если они совпадают и равны 30, значит модель успевает; если инференс 12 fps, а UI показывает 12 fps — система работает правильно, просто модель медленная.

### 7.5 Деградация без падений

Визуализация и запись — это те части, которые чаще всего ломаются на «необычной» машине, поэтому обе обёрнуты в проверки:

* **`cv::namedWindow` может бросить `cv::Exception`**, если HighGUI собран без backend'а (сервер без X11/GTK). Окно создаётся в `try/catch`; при неудаче программа пишет предупреждение и продолжает работать в headless-режиме — `--record`/`--snapshot` остаются доступны. Так же обёрнуты `imshow`/`waitKey`: если окно закрыли или backend отвалился, цикл не падает, а переключается в headless.
* **`cv::VideoWriter` молча не открывается**, если нужного кодека нет в сборке OpenCV (например, пакет собран без FFmpeg: нет ни `mp4v`, ни `XVID`, но есть `MJPG`). Поэтому `open_recorder()` пробует список кандидатов по расширению файла и берёт первый, который реально открылся, а при полной неудаче подсказывает попробовать `.avi`.

Оба случая — пример общего принципа: **внешняя среда (окно, кодеки, камера) не должна приводить к аварийному завершению**; лучше сообщить и продолжить в урезанном режиме.

### 7.6 Горячие клавиши и отзывчивость окна

`cv::waitKey(1)` вызывается **на каждом кадре**, даже если результата нет. Без этого окно HighGUI не перерисовывается и не получает клавиши. Обработка `q`/`Esc`/`s`/`m`/`b`/`c`/`h`/`1`-`3` собрана в одном `switch` — простой пример того, как UI-поток управляет состоянием рендерера, не трогая конвейер.

## 8. Средства C++, использованные в проекте

Это раздел «что именно из языка здесь есть и зачем». Подробный справочник — в `docs/cpp-notes.md`.

### 8.1 Владение и RAII

* **`std::unique_ptr`** — исключительное владение: `SourcePtr`, `SegmenterPtr` (фабрики возвращают `unique_ptr`, вызывающий код не может случайно скопировать и получить два владельца), `std::unique_ptr<Impl>` (pimpl).
* **`std::shared_ptr<const T>`** — разделяемое **неизменяемое** владение кадром и результатом (см. §3.1). `std::make_shared` создаёт объект и контрольный блок одним выделением памяти.
* **RAII для системных ресурсов.** Дескриптор файла, `mmap`-области, `Ort::Session`, `cv::VideoWriter` освобождаются в деструкторах. Классы с владельческими ресурсами **некопируемы** (`= delete` на копировании) и часто **неперемещаемы** (у `V4l2Source` внутри сырые указатели, и перемещение потребовало бы обнулять их в источнике).
* **`= default` / `= delete`** вместо пустых тел: `virtual ~IVideoSource() = default;` — явно показывает намерение и не мешает оптимизациям.

### 8.2 Полиморфизм

* **Виртуальные интерфейсы** `IVideoSource` и `ISegmenter` — «роль», а не «тип данных», поэтому наследование оправдано. Виртуальный деструктор обязателен: `delete` через `unique_ptr<IVideoSource>` должен вызвать `~V4l2Source()`.
* **`final`** на реализациях (`class V4l2Source final`) — запрещает дальнейшее наследование и даёт компилятору право девиртуализировать вызовы.
* **Pimpl (pointer to implementation)** — `struct V4l2Source::Impl` и `struct OnnxSegmenter::Impl`. Цели: (1) не тянуть `linux/videodev2.h` и `onnxruntime_cxx_api.h` в заголовки (ускоряет сборку и уменьшает связность), (2) менять реализацию без перекомпиляции пользователей класса.
* **Шаблоны там, где нужна статика**: `BoundedQueue<T>`, `LatestValue<T>`, `xioctl<Args...>` (variadic, чтобы не писать по обёртке на каждый `ioctl`).

### 8.3 Современные средства (C++17/20)

| Средство | Где | Зачем |
|---|---|---|
| `std::optional<T>` | `try_pop`, `pop_wait_for` | «значение или ничего» без магических `-1`/nullptr |
| `std::atomic<T>` | счётчики, флаг остановки | неблокирующая передача данных между потоками |
| `std::mutex`, `std::condition_variable`, `std::unique_lock`, `std::lock_guard` | очередь | ожидание с предикатом, RAII-блокировки |
| `std::thread`, `join()` | конвейер | параллельные стадии |
| `std::chrono::steady_clock`, `duration<double, milli>` | метрики, таймауты | монотонное время, явные единицы |
| `std::string_view` | `parse_log_level`, `to_string` | чтение без копирования строк |
| `std::filesystem` (в CMake-скриптах/тестах — нет, чтобы не тянуть лишнее) | — | — |
| structured bindings (`auto [k, v] : args`) | CLI | читаемость обхода |
| `enum class` | `OverflowPolicy`, `NextStatus`, `Layout`, `LogLevel` | типизация без неявных преобразований в int |
| `[[nodiscard]]`, `noexcept` (точечно) | API | контракты: «не игнорируй ошибку», «не бросает» |
| `static_assert` | `signal_flag.cpp` | проверка инварианта на этапе компиляции |
| `constexpr`/`constexpr std::array` | палитра, константы | вычисления на этапе компиляции |

| `std::snprintf` вместо `std::format` | logger, HUD | `std::format` нет в libstdc++ до GCC 13 |

### 8.4 Потокобезопасность: правила проекта

Три уровня, каждый со своей областью:

1. **Неизменяемые разделяемые данные** (`Frame`, `InferenceResult`) — вообще не требуют синхронизации, потому что неизменяемы. Основной приём.
2. **Очереди** — единственное место, где потоки обмениваются «правами владения». Вся синхронизация конвейера локализована в `BoundedQueue`.
3. **Счётчики** — `std::atomic` с `memory_order_relaxed`, потому что они нужны только для отображения и не участвуют в синхронизации других данных.

Железные правила, которые соблюдаются в коде:

* `cv::Mat` **никогда** не шарится для записи. Кадр от камеры — константный, размеченный кадр — локальная переменная UI-потока.
* Исключение не должно вылетать из потока: `capture_loop`, `inference_loop` и `segment()` ловят и логируют.
* Все блокирующие ожидания имеют таймаут — иначе `join()` может повиснуть.
* Порядок захвата мьютексов: всегда один мьютекс за раз (вложенных блокировок нет), поэтому deadlock невозможен по построению.

### 8.5 Обработка ошибок: три стратегии

| Ситуация | Стратегия | Пример |
|---|---|---|
| Ошибка **ожидаемая**, часть нормальной работы | код возврата + `std::string& error` | `source->open(error)`, `segment(..., error)` |
| Ошибка **внутри библиотеки** (ORT, OpenCV) | исключение перехватывается на границе модуля и превращается в код возврата | `catch (const Ort::Exception& e)` в `segment()` |
| Ошибка **неисправимая на этом уровне** | лог + мягкая остановка конвейера | 30 ошибок подряд в `capture_loop` |

Почему не исключения между потоками: `std::thread` при непойманном исключении вызывает `std::terminate()`, а пользователь увидит только «terminate called after throwing…» без контекста.

## 11. Почему такая архитектура, а не альтернативы

| Альтернатива | Почему не выбрана |
|---|---|
| **Один поток, всё последовательно** | задержка = сумма всех стадий, камера простаивает; при медленной модели теряются кадры драйвера |
| **Очередь без ограничения** | память растёт неограниченно, задержка растёт линейно — «эффект догоняющего видео» из видеозвонков |
| **`Block` везде** | камера не может ждать: её буферы конечны, драйвер всё равно потеряет кадры, но уже неуправляемо |
| **Пул потоков на кадры** | бессмысленно: у модели один экземпляр, параллелить инференс разных кадров на CPU — только конкурировать за ядра |
| **`cv::dnn` вместо ONNX Runtime** | не поддерживает часть операторов новых YOLO, хуже диагностика |
| **Qt/ImGui для UI** | `cv::imshow` достаточно для учебной задачи и не добавляет зависимостей; при желании `Renderer` отдаёт готовый `cv::Mat`, который легко показать в Qt |
| **GStreamer для захвата** | мощно, но полностью скрывает V4L2 — а цель проекта в том числе понять V4L2 |

## 11a. Разбор аргументов (`src/app/cli.cpp`)

Своя реализация, ~250 строк, без сторонних библиотек. Две фазы:

1. **Сбор пар «ключ — значение».** Один проход по `argv`: поддерживаются и `--key=value`, и `--key value`. Для этого есть явный список ключей со значением (`key_takes_value`) — иначе парсер не знает, съедать ли следующий аргумент. Неизвестный ключ без `=` считается флагом и сообщается как «неизвестная опция», а не как «не указано значение».
2. **Интерпретация.** Один `if/else if` по ключу, каждый разбор валидируется (диапазоны `--score`, перечисления `--layout`, `--log-level`). Ошибка сразу возвращает `false` с текстом, а `main` печатает справку и код возврата 2 — стандартное поведение CLI.

Почему не `getopt_long`: он плохо сочетается с современным стилем (`--key=value` работает, но код обработки всё равно сводится к `switch`), а `cxxopts`/`CLI11` — лишняя зависимость для учебного проекта. Заодно видно, как устроен «взрослый» разбор: единая валидация, `--help`, коды возврата.

## 12. Куда добавлять трекинг (следующий шаг)

Архитектура готова к этому без переделок:

1. `Pipeline` уже разделяет «получение результата» и «его потребление» — трекер станет **третьей стадией** между инференсом и UI (или частью inference-потока).
2. `InferenceResult` неизменяем, значит трекер может отдавать **новый** результат с добавленными `track_id`, не ломая UI.
3. В `Instance` достаточно добавить поле `int track_id = -1` — рендерер уже умеет подписывать объекты, останется вывести `#id`.
4. Классический SORT/ByteTrack требует **матрицы стоимостей** IoU между текущим и предыдущим кадром — координаты боксов уже в пикселях исходного кадра, приведение не нужно.
5. Для проверки трекинга пригодится `--delay-ms` и `--file` (повторяемое видео с известными объектами).

## 13. Ограничения текущей версии (сознательные)

* **Нет переподключения камеры**: при физическом отключении конвейер останавливается (после 30 ошибок подряд). Для продакшена нужен retry-цикл с backoff.
* **Нет записи «сырого» потока отдельно** — пишется мозаика, как видит пользователь.
* **Одна модель, один экземпляр** — нет батчинга и нет ансамблей.
* **CPU-путь препроцессинга** — `blobFromImage` копирует данные; на GPU-пути выгоднее писать в `Ort::Value` с памятью на устройстве.
* **`cv::imshow`** ограничивает частоту обновления скоростью HighGUI (GTK/Qt backend); для 60+ fps нужен свой рендер (OpenGL/SDL). Если HighGUI собран без backend'а, программа предупреждает и работает в headless-режиме (запись/снимки).
* **Число коэффициентов масок зашито как 32** — это стандарт YOLO-seg; при другой модели его нужно выводить из формы выхода.
