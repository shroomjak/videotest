# Механика проекта: от байтов камеры до track_id на экране

Документ объясняет, что происходит с кадром на каждом шаге и почему сделано именно так. Соответствие коду — по файлам в `src/`.

---

## 1. Общая картина

```
 ┌───────────────┐   ┌───────────────────┐   ┌─────────────────────┐   ┌────────────────────┐
 │ V4l2Source    │──▶│ Queue<FramePtr>   │──▶│ Segmenter + Tracker │──▶│ Queue<ResultPtr>   │
 │ поток 1       │   │ ёмкость 2         │   │ поток 2             │   │ ёмкость 2          │
 │ poll → DQBUF   │   │ старое вытесняется │   │ ONNX + Калман       │   │ старое вытесняется │
 └───────────────┘   └───────────────────┘   └─────────────────────┘   └─────────┬──────────┘
                                                                                 ▼
                                                        ┌──────────────────────────────────┐
                                                        │ main: [ кадр | кадр+разметка ]   │
                                                        │ + HUD, клавиши                   │
                                                        └──────────────────────────────────┘
```

Три вещи, из которых складывается вся «реальность времени»:

1. **камера диктует темп** (30 кадров/с = каждые 33 мс), и её драйвер имеет конечное число буферов;
2. **модель непредсказуема по времени** (10–50 мс на кадр);
3. **экран должен показывать свежее**, а не догонять очередь.

Отсюда: камера и модель — в разных потоках, между ними очередь **ёмкостью 2**, которая при переполнении **выбрасывает старый кадр**. Задержка остаётся постоянной (≈ время инференса + один кадр), а не растёт.

## 2. Кадр как единица данных (`src/frame.hpp`)

```cpp
struct Frame {
    cv::Mat image;                                  // BGR, CV_8UC3
    std::uint64_t id;                               // номер кадра от источника
    std::chrono::steady_clock::time_point captured; // когда пришёл от драйвера
};
using FramePtr = std::shared_ptr<Frame>;

struct Instance {           // найденный объект
    cv::Rect box;           // целые пиксели исходного кадра
    float score;
    int class_id;
    int track_id;           // -1 до первого присвоения трекером
    cv::Mat mask;           // CV_8UC1 0/255; может быть пустой
};

struct Result {
    std::shared_ptr<const Frame> frame;  // к какому кадру относится разметка
    std::vector<Instance> instances;
    double infer_ms, latency_ms;
};
```

Почему так:

* **`shared_ptr`**. Кадр нужен сразу в двух местах: в очереди и в результате. `cv::Mat` внутри тоже дешёвый дескриптор, но `shared_ptr` делает время жизни явным и позволяет не копировать пиксели.
* **`const Frame` внутри `Result`**. Разметка — снимок: пока UI рисует по нему, поток обработки уже занят следующим кадром. Запись невозможна → гонки нет без единого мьютекса вокруг данных.
* **`steady_clock`, а не `system_clock`**. Время для задержек должно быть монотонным, иначе скачок системных часов даст отрицательную латентность.
* **`track_id` в `Instance`**, а не отдельная структура трека: рендереру и потребителю нужны только два числа — бокс и id.

## 3. Захват: V4L2 (`src/streams/v4l2_source.cpp`)

### Последовательность вызовов

```
open(/dev/videoX, O_RDWR|O_NONBLOCK)
  VIDIOC_QUERYCAP     — есть ли capture + streaming (через device_caps!)
  VIDIOC_S_FMT        — ЯВНО заданный формат и размер
  VIDIOC_S_PARM       — запросить fps (многие камеры игнорируют — предупреждение)
  VIDIOC_REQBUFS      — N буферов в режиме MMAP
  VIDIOC_QUERYBUF+mmap — спроецировать буферы в своё адресное пространство
  VIDIOC_QBUF × N     — отдать буферы драйверу
  VIDIOC_STREAMON
цикл: poll(fd, 500 мс) → VIDIOC_DQBUF → конвертация в BGR → VIDIOC_QBUF
```

### Решения, которые важно понять

* **mmap вместо `read()`.** Драйвер пишет кадр прямо в память, отображённую в наш процесс: нет промежуточной копии и нет выделения буфера на каждый кадр. Копия остаётся только при конвертации формата (её делает OpenCV).
* **`poll()` перед `DQBUF`.** Файл открыт с `O_NONBLOCK`, поэтому `DQBUF` без данных вернул бы `EAGAIN`, и пришлось бы крутиться в busy-loop, съедая ядро. `poll` спит в ядре и просыпается по готовности кадра **или по таймауту** — это же даёт возможность проверять флаг остановки.
* **`QBUF` обязателен всегда.** После `DQBUF` буфер принадлежит нам; если не вернуть его, через `buffer_count` кадров драйверу нечего заполнять, и камера встанет. Поэтому `QBUF` вызывается даже если конвертация не удалась.
* **`step` (`bytesperline`) в `cv::Mat`.** Длина строки в памяти может быть больше `width × bytes_per_pixel` из-за выравнивания. Если не передать `step`, картинка «поедет» по диагонали — классическая ошибка.
* **`device_caps`, а не `capabilities`.** У камеры с микрофоном `capabilities` описывает всё устройство; возможности конкретного узла `/dev/videoX` — в `device_caps`. Проверка только по `capabilities` ложно отвергает часть камер.
* **Формат не подбирается.** Запросили `MJPG` — либо получили `MJPG`, либо ошибку с подсказкой `v4l2-ctl --list-formats-ext`. Это сознательно: автоперебор скрывает, что реально работает.
* **MJPG vs YUYV.** MJPG меньше по USB (камера сжимает), но требует `imdecode` (единицы мс). YUYV не декодируется, но по USB 2.0 на 1280×720@30 не всегда влезает.
* **RAII.** Деструктор: `STREAMOFF → munmap → close`. Порядок обязателен: отображение памяти закрытого дескриптора использовать нельзя.

## 4. Очередь между потоками (`src/bounded_queue.hpp`)

```cpp
template <class T> class Queue {
    std::size_t push(T value);   // всегда принимает; при полной очереди вытесняет старый
    std::optional<T> pop(duration timeout);  // ждёт данные не дольше timeout
};
```

* **`std::mutex` + `std::condition_variable`** — минимум для «подождать данные». `wait_for` с предикатом (`items_` не пуст) обязателен: `condition_variable` может проснуться сам по себе.
* **`std::unique_lock` в `pop`** — `wait_for` должен отпустить мьютекс на время сна и снова его взять; `lock_guard` этого не умеет.
* **Вытеснение вместо блокировки.** `push` никогда не ждёт: если модель отстаёт, бессмысленно обрабатывать кадр, снятый полсекунды назад. Возвращаемое число вытесненных элементов идёт в счётчик `dropped` — по нему в HUD видно, что модель не успевает.
* **Таймаут в `pop`.** Иначе поток-обработчик, ожидая кадр, никогда не узнал бы об остановке.

Это единственное место, где потоки синхронизируются. Всё остальное (кадры, результаты) — неизменяемые объекты.

## 5. Модель (`src/model/segmenter.cpp`)

### Вход

Модель ждёт `float32 [1, 3, 640, 640]`, значения `[0,1]`, порядок **RGB**.

```cpp
scale = min(640/w, 640/h);                       // letterbox: сохраняем пропорции
canvas 640x640 ← resize(bgr, w*scale, h*scale) по центру, поля 114
blobFromImage(canvas, blob, 1/255, swapRB=true)   // BGR→RGB, HWC→NCHW, /255
```

Почему letterbox: обычный `resize` в квадрат растягивает кадр, и обратное преобразование координат даёт смещение, разное по осям. `scale` и `pad` сохраняются как одно преобразование на прямой и обратный ход — забыть применить их согласованно невозможно.

`Ort::Value` создаётся **на памяти blob'а** (`CreateTensor` + `blob.ptr<float>()`): данные не копируются, живут до конца `Run()`.

### Выходы: два явных формата

**`--out-layout raw`** (YOLOv8-seg, YOLO11-seg):

```
output0: [1, 4+nc+32, 8400]   — предсказания по всем якорям
output1: [1, 32, 160, 160]    — 32 прототипа масок
```

Раскладка канал-мажорная: значение канала `c` для якоря `a` — по адресу `c * 8400 + a`. Строки `cx, cy, w, h`, затем `nc` вероятностей, затем 32 коэффициента масок. Декодер (`decode_raw`) читает ровно по этой формуле.

**`--out-layout nms`** (YOLO26, end-to-end):

```
output0: [1, 300, 38]   — 300 готовых детекций
output1: [1, 32, 160, 160]
столбцы: x1, y1, x2, y2, score, class_id, 32 коэффициента
```

Здесь NMS уже выполнен внутри графа (one-to-one head) — повторять его в C++ нельзя: можно удалить легитимно перекрывающиеся объекты.

**Почему формат не определяется автоматически.** Формы `[1, 4+nc+32, 8400]` и `[1, 300, 6+32]` при малом `nc` отличаются только числами, а неоднозначность в этом месте превращается в «разметка пустая, но почему — непонятно». Пользователь говорит, какой у него экспорт, программа печатает фактические формы выходов при загрузке — расхождение видно сразу.

### NMS (`Segmenter::suppress`)

Гасим дубликаты **в пределах класса**:

```
сортируем по убыванию score
берём лучший непогашенный бокс, оставляем
гасим все следующие того же класса с IoU > 0.45
```

Class-aware — принципиально: человек и чашка перекрываются, подавление по всем классам склеило бы их. IoU = пересечение / объединение; на пустом объединении возвращаем 0 (без деления на ноль).

### Маски (`Segmenter::make_masks`)

Модель не выдаёт маску на объект: она выдаёт **базис из 32 «мягких» масок** (прототипы 160×160) и **32 коэффициента на объект**. Маска объекта — линейная комбинация:

```
mask(x,y) = sigmoid( Σ_k coeff[k] · proto[k,y,x] )
```

Шаги: накопить `Σ coeff·proto` в `CV_32F` 160×160 → обрезать по боксу (в масштабе прототипов `160/640`) → `resize` к боксу в пикселях кадра → порог → вставить в пустое изображение размера кадра.

Порог считается в логитах: `sigmoid(v) > t` ⟺ `v > log(t/(1−t))` — одно `compare` вместо `exp` на каждый пиксель.

## 6. Трекинг (`src/track/tracker.cpp`)

Принцип SORT, но без внешних библиотек — только `cv::KalmanFilter` из модуля OpenCV `video`.

### Состояние трека — 8 чисел

```
cx, cy, w, h        положение и размер
vx, vy, vw, vh      скорости тех же величин
```

Матрица перехода `F` кодирует «равномерное движение»: `position += velocity`. Поэтому `predict()` — это `state = F * state`, то есть один проход по матрице. Матрица измерений `H` (4×8) берёт из состояния только позицию/размер: детекция не знает скоростей.

### Что происходит за кадр

```
1. predict:   для каждого трека state = F * state; box = state → Rect
2. associate: для всех пар (детекция, трек) считается IoU;
              пары с IoU >= 0.3 сортируются по убыванию;
              жадно забираем пары без повторов (одна детекция — один трек)
3. update:    matched: kalman.correct(измерение), track_id проставляется;
              unmatched детекции: новый Track (id = next_id++), Калман инициализируется
4. age:       трек без детекции: missed++; если missed > max_age (15) — удалить
```

Почему жадное сопоставление, а не венгерский алгоритм: на 10–50 объектах разница в качестве меньше, чем в сложности кода; для учебного проекта важен сам механизм.

Почему Калман вообще нужен: бокс от детектора дрожит кадр к кадру, а на пропущенных кадрах детекции нет совсем. Калман даёт гладкую траекторию и позволяет «догадаться», где объект, пока его не видно.

### Почему id не путаются

Пара сопоставляется только по IoU с текущим предсказанным положением. Если объект резко прыгнул (IoU < 0.3) — потеряется старый трек и появится новый, но чужой id новому объекту не достанется.

### Что делать с этим дальше

Улучшения по возрастанию сложности: венгерский алгоритм вместо жадного; отдельные пороги IoU на «рождение» и «сопровождение»; каскадное сопоставление по цвету/маске; DeepSORT с эмбеддингами. Всё это вставляется в `associate()` и не затрагивает остальной конвейер.

## 7. Конвейер и остановка (`src/pipeline.cpp`)

```cpp
capture_loop:  while (running && !stop) { grab → push(frame) }
process_loop:  while (running && !stop) { pop(100ms) → infer → tracker → push(result) }
```

* Потоков **два**: захват не должен ждать модель. Если объединить, время кадра станет `t_grab + t_infer`, а задержка вырастет на инференс.
* **`stop()`**: сначала `running_ = false`, потом `join()`. Обратный порядок (сначала `join`) — гарантированный дедлок: рабочие циклы крутятся по флагу, который никто не снял. Это проверено смоук-тестом.
* **Двойная защита от ошибок**: одиночный сбой камеры/модели не убивает конвейер (лог + continue), но 30 (камера) / 20 (модель) ошибок подряд останавливают его, чтобы не молотить вхолостую.
* **Ctrl+C**: обработчик сигнала только выставляет `std::atomic<bool>` — единственное, что разрешено в асинхронном контексте (мьютексы/`printf`/`malloc` там запрещены). Циклы `poll` и `pop` просыпаются по таймауту и видят флаг.

## 8. Визуализация (`src/render/renderer.cpp`)

```
raw     = result->frame->image              // исходный кадр
overlay = draw_overlay(raw, instances)      // маски + боксы + "#id cN score"
canvas  = hconcat(raw, overlay)             // два потока рядом
draw_hud(canvas, {...})                     // счётчики
```

* **Один `addWeighted` на все маски.** Если накладывать каждую маску отдельно, в местах перекрытия альфа складывается и пятно темнеет. Здесь маски красятся в отдельный слой и смешиваются с кадром один раз.
* **`findContours` — на копии маски.** Функция модифицирует входную матрицу (историческая особенность OpenCV), а `Instance.mask` может читаться в другом потоке.
* **Пустая разметка = нет масок.** Если модели нет, `instances` пуст, `draw_overlay` возвращает обычный клон кадра, и правая половина совпадает с левой. Отдельного режима «без модели» нет — конвейер всегда один и тот же.
* **Окно может отсутствовать.** `namedWindow` бросает `cv::Exception`, если HighGUI собран без backend'а (сервер без X11): обрабатываем и продолжаем без окна, оставляя `--snapshot`/`--max-frames`.

## 9. Средства C++, которые здесь реально используются

| Средство | Где | Зачем |
|---|---|---|
| `shared_ptr` / `shared_ptr<const T>` | `FramePtr`, `Result::frame` | разделяемое владение без копирования пикселей |
| `unique_ptr` | `Ort::Session` внутри `OrtHolder` | владение ресурсом ONNX Runtime |
| RAII (деструкторы) | `V4l2Source`, `Segmenter`, `Pipeline` | `STREAMOFF/munmap/close`, остановка потоков |
| `std::thread` + `join` | конвейер | две стадии параллельно |
| `std::mutex`, `condition_variable`, `unique_lock` | `Queue` | ожидание данных с предикатом и таймаутом |
| `std::atomic` | счётчики, флаг остановки | чтение метрик и сигнал без блокировок |
| `std::optional` | `Queue::pop` | «данных нет» без магических значений |
| `std::chrono::steady_clock` | метрики, таймауты | монотонное время |
| шаблон класса | `Queue<T>` | одна реализация для кадров и результатов |
| `enum`/строки-конфиги | формат камеры, layout модели | явный контракт вместо автодетекта |
| `= delete` на копировании | `V4l2Source`, `Segmenter`, `Pipeline` | запрет копирования объектов с ресурсами |
| `override`/`final` | все реализации `Source`, `V4l2Source` | ловля ошибок сигнатур компилятором |
| pimpl «руками» | `Segmenter::OrtHolder` | `onnxruntime_cxx_api.h` не тянется в заголовок |
| `try/catch` на границе потока | `Segmenter::infer`, потоки конвейера | исключение в `std::thread` = `std::terminate` |

Чего здесь **сознательно нет**: `std::jthread`, `std::format`, `std::ranges`, внешних библиотек кроме OpenCV и ONNX Runtime, шаблонных фабрик и «умных» настроек. Задача — увидеть механику, а не спрятать её.
